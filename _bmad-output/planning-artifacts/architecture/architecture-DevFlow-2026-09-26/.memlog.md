- (constraint) Herdr is the optional execution observation layer; the harness owns state, Gates, locks, error store, benchmark — not Herdr.
- (constraint) v1 ships exactly one pipeline: `software-v1` with six fixed steps in fixed order: research → design → coding → testing → review → delivery.

- (decision) PARADIGM: layered + ports-and-adapters hybrid (load-bearing). Three horizontal layers: ① Harness control plane (owns state, gates, locks, error store, benchmark) → ② BMAD method layer (per-step skills, pinned by version) → ③ Execution layer (Agent + LLM, optionally observable by Herdr). Inside each layer, ports-and-adapters: the harness depends only on a Step Executor Port + a Herdr Event Port; concrete agents and Herdr are adapters. Why layered: PRD §3 + brief addendum §2 already name the three layers; the layers are stable across all FRs; layering loads a known model (top-down dependencies, no upward calls). Why ports-and-adapters: PRD G3 + FR-5/FR-7/FR-28 require Agent/LLM/Herdr to be swappable without changing the harness — only a port interface achieves that. Hexagonal alone (no layers) would not enforce "harness controls, Herdr observes"; pipes-and-filters would erase the gate/lock/error-store as first-class; CQRS would over-shape the data path.
- (decision) DEPENDENCY DIRECTION (rule): Harness may depend on Method layer contracts (Skill manifest, artifact contract). Method layer MAY NOT depend on Harness. Execution layer (Agent adapters + Herdr event sink) MAY NOT depend on Harness internals — only on the Step Executor Port and Herdr Event Port. Herdr MAY NOT depend on Harness — it emits events; the Harness ingests them. This freezes the three-layer order and prevents the harness from being hollowed out by the method layer calling back, and prevents Herdr from quietly becoming the control plane.
- (decision) HARNESS COMPONENTS (names fixed at initiative altitude, seed only — code owns the detail): (a) Workflow Controller — fixed six-step pipeline `software-v1`; refuses edits (FR-2). (b) Project Manager — project YAML + run lifecycle + mid-project executor swap (FR-4/FR-7). (c) Artifact Store — content-addressed (sha256:), immutable post-lock, append-only writes during pending (FR-9/FR-11/FR-17). (d) Gate Engine — Acknowledgement records, skipped-Gate semantics for trivial/session tiers (FR-10/FR-12). (e) Error Store — append-only structured records (FR-13/FR-14). (f) Retry Manager — retry ladder rungs 1–5 with rung-4 Skill-pending-promotion guard (FR-15). (g) Regression Set + Benchmark Engine — regression-set health floor K=3 (NFR-Reliab-3), metric-defined (FR-20/FR-21). (h) Skill Bump Registry — pinned BMAD Skills, regression-gated, manually promoted (FR-6/FR-22/FR-23). (i) Operator Dashboard — run status, error store, regression diff, benchmark output, cost surface (FR-24–27 + NFR-Cost-1). (j) Cost Guard — per-tier ceilings + cost_overrun_ack pause (NFR-Cost-2). (k) Step Executor Port — the only harness surface that touches Agent/LLM/executor adapters.
- (decision) EXECUTOR PORT (Step Executor Port): one stable harness-facing interface per step invocation. Methods: `prepare(input_artifact_hash, executor_tuple, skill_manifest) → invocation_handle`; `start(handle) → step_run_id`; `status(step_run_id) → state`; `output(step_run_id) → pending_artifact`; `cancel(step_run_id)`. Executor Tuple is the only typed input: `{mode: human|agent, agent?, model?, skills: [<skill>@<version>]?, human_first_stories?, story_gates?}`. Every Agent adapter (Pi / OMP / Codex / Claude Code / DSH) implements this port. Herdr is NOT behind this port — Herdr is a separate event-sink port (k2).
- (decision) HERDR EVENT PORT: separate, narrower port. Herdr emits append-only signed events `{executor_id, step, project_id, started_at, ended_at, outcome}` (FR-29). Harness ingests events for telemetry only — events do NOT drive state transitions, gate verdicts, or retry-ladder decisions (FR-28). A Herdr outage MUST NOT block a run (NFR-Reliab-2 implies the run resumes without Herdr). The harness-direct Step Executor Port is the primary invocation path; Herdr is observational.
- (decision) AD-1 Pipeline Immutability [ADOPTED]: Binds FR-1, FR-2. Prevents: a project YAML, skill bump, or operator action silently adding/removing/reordering steps in `software-v1` (which would invalidate every locked artifact and every comparable run). Rule: the pipeline definition `software-v1` is loaded once at harness boot; its step list and per-step artifact contracts are immutable for the life of the process. Bumps are new versions (`software-v2`), not mutations. Returns `pipeline_immutable` on edit attempts. Storage: pipeline definitions live under `pipelines/<name>@<version>.yaml` and are read-only at runtime.
- (decision) AD-2 Pipeline Routing = Project Binding [ADOPTED]: Binds FR-1, FR-4, OQ-1 (router location). Prevents: every project hand-wiring its own step sequence (which would defeat the "fixed workflow" differentiator) AND the v1 router being a separate sidecar service that introduces an unrelated deploy surface and trust boundary (per PRD addendum §A8 item 1 + D1). Rule: the v1 static router is in-process — the Workflow Controller IS the router. It reads each step's executor tuple from the project YAML and hands off to the Step Executor Port. The router surface is a single function: `route_step(project_id, run_id, step) → executor_tuple`. Dynamic router (success-rate-based selection) is deferred to v2 (D6).
- (decision) AD-3 Artifact Lock = Content-Addressed + Signed [ADOPTED]: Binds FR-11, FR-17, NFR-Reliab-1, NFR-Sec-1. Prevents: two units (writer + reader) computing different hashes for the same content, or one unit mutating a locked artifact without detection — both would invalidate UJ-3's audit-from-hashes story. Rule: every artifact write computes `sha256:` over canonical bytes; on lock, the harness appends a signature covering `(hash, project_id, run_id, step, lock_timestamp)` using the harness key. Locked artifacts are read-only. Any write attempt returns `artifact_locked`. Hash mismatch on read returns `artifact_corrupt`.
- (decision) AD-4 Error Store = Append-Only Immutable Log [ADOPTED]: Binds FR-13, FR-14, NFR-Reliab-3 (justification audit). Prevents: an operator silently editing or deleting error records (which would let the audit story UJ-3 collapse) OR the retry ladder being collapsed (which would make the error store lie about which rung failed). Rule: the error store is a single append-only ledger keyed by `record_id`. Each record is `{record_id, project_id, run_id, step, attempt, category, root_cause[], correction[], retry[], result, recorded_at, hash}`. Records are immutable post-write. `regression_set_remove` is a separate ledger entry (see AD-7). Returns `error_store_immutable` on edit/delete attempts.
- (decision) AD-5 Acknowledgement Record Shape [TENTATIVE — D5 territory]: Binds FR-10, NFR-Sec-2. Prevents: human Gate approvals being forgeable (a comment on the wrong commit, a screenshot) OR automated approvals being indistinguishable from human ones. Rule: every Acknowledgement is a signed JSON record `{acknowledgement_id, project_id, run_id, step, acknowledger, acknowledger_kind: human|check, verdict: accepted|accepted-with-open-items|rejected, open_items[]?, signed_hash, timestamp}` persisted under `acknowledgements/<project_id>/<run_id>/<step>/`. Signatures use the harness key (human approvals sign via the operator console; check approvals sign via the check runner). Unsigned records are rejected with `acknowledgement_unsigned`. Skipped-Gate path (FR-12 trivial/session tiers) writes NO Acknowledgement record; the step-end run event carries `gate_mode: skipped` + implicit `verdict: accepted` per FR-10 clause.
- (decision) AD-6 Skill Pin Enforcement + Bump Ladder [ADOPTED]: Binds FR-6, FR-22, FR-23, OQ-4. Prevents: BMAD Skill auto-upgrade silently breaking locked artifacts (which would invalidate the audit story), or the retry ladder silently consuming a non-promoted Skill (which is what PRD review-flag #1 calls out). Rule: project YAML must pin every Skill as `name@version`; unpinned = load-time `skill_pin_required` error. A proposed version bump (x.y.z → x.y.z+1) is registered in the Skill Bump Registry and gated by a regression run on the affected steps (FR-22). Bumps are held in `pending_promotion` until an operator manually promotes (FR-23). The retry ladder rung 4 may ONLY use a Skill from the operator-promoted set; otherwise the harness returns `skill_not_promoted` and pauses for operator action.
- (decision) AD-7 Regression Set = Immutable History + Health Floor [ADOPTED]: Binds FR-18, FR-20, NFR-Reliab-3, SM-C1. Prevents: a benchmark query recommending from a regression set that has been silently shrunk (PRD review #2 — "regression-set evaporates with churn") or from raw success rate (PRD counter-metric SM-C1). Rule: (a) regression set additions are append-only; (b) `regression_set_remove` requires a written justification and is itself recorded as an audit event `{removed_run_id, removed_at, removed_by, reason}`; (c) `bench <step>` returns `regression_set_insufficient` when comparable-run count for `step × project-size-tier` cell is below K=3; (d) metric definition is recorded with every benchmark run, so two metrics on the same set produce distinct, traceable recommendations; (e) cross-tier mixing without explicit override returns `non_comparable_set`.
- (decision) AD-8 Per-Tier Cost Ceiling + Pause [ADOPTED]: Binds NFR-Cost-1, NFR-Cost-2, FR-15, FR-22, FR-7. Prevents: a retry-ladder chain or a Skill-bump regression pass silently consuming the entire project LLM budget (PRD adversarial review #1 — "cost story is telemetry, not a ceiling"). Rule: each project-size-tier carries a default ceiling (`trivial` ≤ 5e5, `session` ≤ 5e6, `epic` ≤ 5e7, `project` ≤ 2e8 logged tokens). Skill-bump regression pass = 3× the affected step's normal ceiling. On overrun, the harness pauses the next step invocation and requires `cost_overrun_ack` from an operator before resuming. Ceilings are configurable per project YAML.
- (decision) AD-9 Herdr Scope = Observation Only [TENTATIVE — D3 territory, needs review]: Binds FR-28, FR-29, NFR-Privacy-1, OQ-3. Prevents: Herdr quietly becoming the control plane (which would invalidate the brief addendum §7 #1 + PRD §5 "Not a control plane for Herdr" + the brief addendum §2 three-layer rule). Rule: Herdr emits append-only signed events to the Herdr Event Port; the harness ingests events as telemetry only — events do NOT drive gate verdicts, retry decisions, artifact locks, or run-state transitions. Herdr outage MUST NOT block a run (NFR-Reliab-2 implies resume without Herdr). Executor lifecycle (start/stop/restart) is NOT a v1 Herdr concern; the harness invokes adapters directly via the Step Executor Port. If OQ-8 picks Herdr as the actual execution layer, this AD is rescoped and Herdr gets a `k_execute` port instead of a `k_observe` port — but that is the OQ-8 fork.
- (decision) AD-10 Executor Adapter Auth + Threat Model [NEW — closes PRD adversarial #3]: Binds FR-28 consequence, FR-7 (mid-project swap), NFR-Sec-1, NFR-Sec-2. Prevents: a compromised or impersonated executor receiving locked artifact inputs, OR an executor tuple swap silently exfiltrating state (PRD adversarial #3 + #4 — "swap has no threat model"). Rule: (a) every Step Executor Port call carries a harness-signed invocation token `{invocation_id, project_id, run_id, step, executor_tuple_hash, expires_at}`; (b) each Agent adapter validates the harness signature before reading locked inputs; (c) the executor tuple hash is recorded on the run event so audit can prove which tuple was authorized; (d) v1 ships with 1–2 adapters (per PRD §6.2 — to be picked in bmad-spec); each adapter ships its own auth-handshake story in its adapter manifest (auth mode: bearer / oauth / cli-resident — declared in the manifest, not in the harness).
- (decision) AD-11 Done vs Locked Distinction [NEW — closes PRD review rubric FR-10/FR-12 gap]: Binds FR-10, FR-12, Glossary "Done". Prevents: `trivial`/`session` tier runs being recorded as Gate-Acknowledged when no Acknowledgement exists, which would inflate audit metrics and confuse operators (PRD rubric finding "FR-10 vs FR-12 reconciliation missing"). Rule: `locked` requires a Gate verdict (FR-11). `Done` is the `trivial`-tier (and session-tier skipped-Gate) terminal state — NO Acknowledgement record is written; the step-end run event carries `gate_mode: skipped` + an implicit `verdict: accepted` + `confirm_id` for the operator confirm (FR-12 + Glossary "Done"). Dashboard distinguishes `Completed (Done)` from `Locked (Acknowledged)` (FR-24). Skipped Gates are NEVER recorded as explicit Acknowledgements.
- (decision) AD-12 Verdict Vocabulary = Three-Valued [NEW — closes PRD rubric gap]: Binds FR-9, FR-10. Prevents: an `accepted-with-open-items` state being unreachable in the Acknowledgement record path (PRD rubric finding "verdict vocabulary gap"), which would force operators to either reject-and-restart or accept-and-bury. Rule: Acknowledgement `verdict` is the closed enum `accepted | accepted-with-open-items | rejected`. `accepted-with-open-items` transitions the artifact to `locked` and attaches an `open_items[]` field of `{item_id, description, owner, severity}` to the Acknowledgement record. `rejected` blocks the next step and writes an error record (FR-13).
- (decision) AD-13 Operator Dashboard = Read Model over Stores [ADOPTED]: Binds FR-24, FR-25, FR-26, FR-27, NFR-Cost-1. Prevents: the dashboard becoming a second writer (which would create write contention with the canonical stores) or hiding state transitions (FR-9 / FR-11) from operators. Rule: the dashboard is a read-model layer that projects from the canonical stores (Artifact Store, Error Store, Regression Set, Run Event log, Cost log). No write paths exist in the dashboard except Acknowledgement (signed via the harness key — AD-5). Every dashboard view is a pure function of `(project_id, run_id, store_snapshot_at_query_time)`.
- (decision) AD-14 Run Event Log = Source of Truth for Observability [ADOPTED]: Binds NFR-Obs-1, NFR-Obs-2, NFR-Reliab-2, FR-19. Prevents: dashboard metrics being computed from log scraping (which would fail UJ-3 audit-from-hashes) OR a crash mid-step losing run state. Rule: every harness state transition writes one append-only run event `{event_id, project_id, run_id, step, executor_tuple, started_at, ended_at, outcome, gate_mode, cost_tokens_in, cost_tokens_out, confirm_id?, error_record_id?, acknowledgement_id?}` to the Run Event Log. Run state is reconstructable from the event log alone (NFR-Reliab-2). Cost telemetry is logged here and surfaced via the dashboard (NFR-Cost-1).
- (decision) AD-15 Six-Step Sequence is Wired, Not Configurable [ADOPTED]: Binds FR-1, FR-2, SM-1. Prevents: a project YAML or operator action skipping steps in `software-v1`, which would invalidate SM-1's "100% of runs use the six fixed steps" success metric AND the audit story (locked chain breaks). Rule: the harness enforces `software-v1` step order as code — the only legal transitions are research → design → coding → testing → review → delivery. Skip is achieved via the size-tier Gate-strictness rules (FR-12: trivial/session tiers use `gate_mode: skipped` to bypass Acknowledgement, NOT to bypass the step itself). A run with an unresolved prerequisite step is held `pending` and `step_unreachable` is returned on attempted launch.
