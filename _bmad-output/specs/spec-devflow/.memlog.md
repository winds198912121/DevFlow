- (decision) Why = mandate-meet + opportunity-capture combination: PRD exists with finalized FRs (29), NFRs (13), UJs (3), and spine has 26 ADs already adopted; this SPEC.md condenses them into the kernel every downstream skill consumes. Pain: agents are interchangeable-for-user, opaque-underneath; opportunity: harness layer is the missing piece on top of BMAD Method skills. Single-tenant, single-org, single-team, software-v1 only.
- (capability) CAP-1 (run pipeline): operator can launch a project against pipeline software-v1 and the harness executes the six fixed steps research → design → coding → testing → review → delivery in that order; success = 100% of runs on software-v1 traverse all six steps in order (SM-1) and a closed project is reproducible from artifact hashes + executor tuples alone (NFR-Reliab-2).
- (capability) CAP-2 (swap executor mid-project): operator can change a step's Agent/LLM/Skills pin between runs and resume without re-executing previously locked steps; success = locked artifacts of prior steps remain unchanged (FR-11) and the previous executor's artifacts are retained in history (FR-7).
- (capability) CAP-3 (gate acknowledgement): every step's Gate produces a signed Acknowledgement record (acknowledgements/<project_id>/<run_id>/<step>/<acknowledgement_id>.json) that gates the next step; success = unsigned or path-mismatched records are rejected (NFR-Sec-2 + AD-23 path-triple signature) and a closed project's Gate history is reproducible from artifact hashes + acknowledgements directory alone (UJ-3).
- (capability) CAP-4 (structured error store + retry ladder): every failed step writes an append-only error record with category, root_cause, correction, retry[], result; the harness offers the next retry-ladder rung in order same → same LLM → better LLM → different agent+skill → human, with rung 4 only consumable on operator-promoted Skills; success = ≥ 95% of failures logged (SM-3) and no rung is silently skipped.
- (capability) CAP-5 (benchmark-driven recommendation): bench <step> returns a recommended Agent/LLM/Skills tuple from a regression set, not from raw success rate; success = a recommendation per step within 3 projects of usage (SM-4), and bench refuses (regression_set_insufficient) when fewer than K=3 comparable runs exist for the step × project-size-tier cell (NFR-Reliab-3).
- (capability) CAP-6 (Skill bump gate): a proposed BMAD Skill version bump must pass the regression set on affected steps before an operator can manually promote it; success = 0 promoted regressions (SM-5) and bumps that fail are recorded with per-step results (FR-22).
- (capability) CAP-7 (operator dashboard read surface): the dashboard surfaces run status, error store (filterable by project/step/category/agent/executor-tuple/date), regression diffs for skill bumps, and benchmark output; success = every dashboard view is a pure function of canonical stores (AD-13) with the only writes enumerated by AD-21.
- (capability) CAP-8 (cost guard): the harness pauses the next step on per-tier token ceiling overrun and requires operator cost_overrun_ack before resuming; success = a retry-ladder chain or Skill-bump regression pass cannot silently consume the project budget (NFR-Cost-2) and cost telemetry is logged per step (NFR-Cost-1).
- (constraint) Pipeline software-v1 step list, order, and per-step contracts are immutable at runtime (FR-1, FR-2, AD-1). Bumping pipeline is software-v2, never an in-place edit.
- (constraint) Executor invocation path is harness-direct via ExecutorAdapter (PRD A6, OQ-8 stance a): harness owns auth + lifecycle + error mapping; Herdr is an out-of-process observability feed that consumes adapter events, never the source of control state. A Herdr outage MUST NOT block a run.
- (constraint) BMAD Skills must be pinned as name@version in project YAML; auto-upgrade is forbidden; the Skill Bump Registry is the only path to a new version (FR-6, AD-6). The retry-ladder rung 4 may ONLY consume a Skill from operator-promoted set; otherwise skill_not_promoted and pause.
- (constraint) Canonical hashing (sha256:) goes through ONE function: harness.canonical.canonical_bytes (AD-17). No unit may compute sha256 directly; CI lint enforces sole importer. Canonicalization: JSON sorted keys + UTF-8 NFC + LF + no trailing newline; text LF + trailing newline; binary as-is.
- (constraint) Locked artifacts, error records, Acknowledgement records, cost-ledger rows, and regression-set rows are immutable post-write; edits return *_immutable / *_locked errors. The error store, run event log, and cost ledger are append-only.
- (constraint) All signing uses Ed25519 with the harness key at var/secrets/harness.key (0600). Unsigned artifacts and unsigned acknowledgements are rejected (NFR-Sec-1, NFR-Sec-2). Acknowledgement signatures cover (acknowledgement body + storage path triple) to defeat copy-paste forgery (AD-23).
- (constraint) Step terminal status has one resolver: harness/gate_engine/step_status(run_id, step) returns {terminal: Done|Locked|Pending|Failed, gate_mode: enforced|skipped, confirm_id?, acknowledgement_id?}. Every dashboard view MUST call this function; no view may compute terminal status inline (AD-24).
- (constraint) Operator dashboard's only write paths are exactly: submit_acknowledgement (AD-5), swap_executor_take_lock (AD-18), trigger_skill_bump_regression (FR-22), promote_skill_bump (FR-23, requires regression_run_id), cost_overrun_ack (AD-8), regression_set_remove (AD-7). FastAPI router enforces this allowlist at import time (AD-21).
- (constraint) Size-tier Gate strictness: trivial = single confirm per step → Done (no formal Gate); session = light Gate on Design only; epic = Gates on all six steps + sub-Gates on key Coding stories + human_first_stories: N; project = full Gate + benchmark feedback (FR-12). Skipped-Gate writes NO Acknowledgement; the step-end run event carries gate_mode: skipped + implicit verdict: accepted (FR-10 / AD-11).
- (constraint) Per-tier cost ceilings (logged tokens in+out, no USD): trivial ≤ 5e5, session ≤ 5e6, epic ≤ 5e7, project ≤ 2e8. Skill-bump regression ceiling = 3× affected step's normal ceiling. On overrun the harness pauses and requires cost_overrun_ack. Ceilings configurable per project YAML (NFR-Cost-2).
- (constraint) Layer dependency direction is enforced by tools/check_layer_boundaries.py in CI: skills/, agents/, and herdr/ MAY NOT import anything under harness.* except the published-port allowlist in harness/ports/__init__.py (AD-26).
- (non-goal) End-user / chat / consumer surface (PRD §5, brief addendum §7 #5). DevFlow is operator dashboards only.
- (non-goal) Wrapping a single agent. DevFlow must support swapping Agent/LLM/Skills per step.
- (non-goal) Replacing BMAD Method skills with method-layer equivalents. DevFlow consumes BMAD Skills (bmod-method), does not redefine per-step contracts.
- (non-goal) Herdr as the control plane. Herdr is observation-only (external observability feed, PRD A6).
- (non-goal) Auto-promotion of BMAD Skill bumps. Manual operator promotion only (FR-23).
- (non-goal) Native fine-tuning of any underlying LLM. DevFlow consumes third-party LLMs.
- (non-goal) Cross-org / multi-tenant platform in v1. Single-org, single-team.
- (non-goal) Pipelines beyond software-v1 (data-v1, ml-v1) in v1. Vision-only.
- (non-goal) Dynamic Agent/LLM router (success-rate-based selection). Deferred to v2.
- (non-goal) Herdr lifecycle management of agents (start/stop/restart). Deferred to v2; harness owns lifecycle via ExecutorAdapter (AD-10).
- (non-goal) Native integration with every Agent in v1. Ship 1-2 adapters; add per executor (PRD §6.2).
- (assumption) v1 deploys single-node self-hosted. No cloud-managed dependency (PRD §6.2, spine Scope).
- (assumption) Operator identity for human acknowledgements is provisioned out-of-band (SSH key, OIDC, or harness-side UI token). Identity-binding UX detail is non-blocker for spec; lands in bmad-ux.
- (assumption) LLM non-determinism is expected: ≥ 90% of locked artifacts have stable hash across identical-input re-renders; below that the platform reports non_deterministic_executor (SM-7).
- (question) OQ-6 — Which 1-2 Agents ship as v1 executor adapters? (PRD OQ-6, spine OQ-6) — required by spine AD-10(d); not required to ship v1 harness binary but blocks any v1 run that wants non- mode for any step.
- (question) OQ-7 — BMAD Skill ownership of each step's artifact contract? PRD addendum §A6 proposes a mapping (research→bmad-deep-recon, design→bmad-prd→bmad-architecture→bmad-spec, coding→bmad-preview-ticketing+bmad-build, review→bmad-retrospective+bmad-code-review); testing + delivery have no BMAD skill. Spec defers ratification; consumers treat the mapping as proposed.
- (question) OQ-1 — Static v1 router location: in-repo (AD-2 in-process) vs sidecar. Spine AD-2 picks in-process; user ratification deferred. If ratified the other way the ExecutorAdapter seam absorbs the router.
- (decision) Success signal: A small (1-5 person) team opens DevFlow, picks pipeline software-v1, points it at a repo, and forgets which Agent ran it — the data point lands in the regression set; after ≥ 3 comparable runs per step, bench <step> returns a data-driven recommendation; six months later, a tech lead can audit a closed project from artifact hashes + the acknowledgements/ directory alone (UJ-1/2/3 realized together).
